Key B — Secondary
Key C — Backup

1. Round Robin
2. Failover
3. Least Recently Used
4. Least Usage, when reliable usage data is available
5. Manual Priority

Support:

- Primary key selection.
- Key priority.
- Enable / Disable individual keys.
- Per-key usage tracking.
- Per-key request counts.
- Last successful request.
- Last error.
- Rate-limit state.
- Cooldown period.
- Key health status.

7.1 Intelligent Rotation

Handle provider errors intelligently.

Examples:

- HTTP 401: Mark the key as authentication-failed; do not repeatedly retry it.
- HTTP 403: Distinguish permission errors from other failures.
- HTTP 429: Respect Retry-After and provider rate-limit information; temporarily defer the affected key.
- HTTP 5xx: Apply bounded retry and backoff where appropriate.
- Network errors: Use bounded retries and eligible fallback keys.

Do not rotate blindly.

Do not retry non-idempotent requests without appropriate safeguards.

Do not treat different keys as independent quotas unless the provider actually guarantees independent limits.

IMPORTANT:

Key rotation must be used for legitimate account management, resilience, and user-configured quota handling.

Never implement mechanisms intended to evade provider restrictions, bypass account-level usage limits, or circumvent billing policies.

Never guarantee that key rotation will bypass provider rate limits or usage limits.

Provide a clear explanation when all available keys are exhausted.

10. SECURITY — CRITICAL REQUIREMENTS

Security must be implemented as part of the architecture, not added later.

10.1 API Key Storage

Never store API keys as plaintext in:

- localStorage
- sessionStorage
- IndexedDB without appropriate encryption
- Unencrypted database columns
- Logs
- Error messages
- Analytics events
- Git repository files

Use the strongest secure storage mechanism supported by the actual application architecture.

Examples:

- Desktop applications: OS credential vault / secure keychain integration.
- Backend applications: encrypted server-side secret storage with appropriate access controls.
- Local-first applications: platform-protected credential storage or an audited encrypted vault.

Use authenticated encryption with sound key management.

Never hardcode encryption keys into source code.

Do not create custom cryptographic algorithms.

If the current architecture cannot securely protect credentials, explicitly document the limitation and implement the safest viable design.

10.2 Credential Handling

- Mask secrets in the UI.
- Reveal secrets only through an explicit user action when supported.
- Never return stored secrets through ordinary API responses.
- Avoid copying secrets into frontend state unnecessarily.
- Prevent accidental secret exposure in crash reports.
- Redact secrets from logs.
- Use secure credential deletion.
- Avoid unnecessary secret duplication.

10.3 Network Security

- Require HTTPS for remote provider endpoints.
- Permit HTTP only for explicitly trusted local/loopback configurations where appropriate.
- Validate custom provider URLs.
- Prevent SSRF and access to unintended internal network destinations.
- Apply network restrictions appropriate to the desktop or server deployment.
- Validate redirects and destination changes.
- Set request timeouts and response-size limits.

10.4 Data Privacy

- Never transmit document content without an explicit AI action.
- Explain which provider receives the selected content.
- Clearly identify external data transmission.
- Avoid collecting unnecessary telemetry.
- Keep document contents out of AI request history by default.
- Do not transmit unrelated application data.

10.5 GitHub Security

- Never commit API keys.
- Never commit personal credentials.
- Audit environment files and configuration examples.
- Add suitable .gitignore entries.
- Add secret scanning where available.
- Add dependency security checks.
- Add security-focused tests.
